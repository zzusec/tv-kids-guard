需要 JDK 17、Android SDK 35、build-tools 35.0.0 和 Python 3。用 ANDROID_HOME 或本机 local.properties 的 sdk.dir 指定 SDK。

Android 4.4 兼容

最低版本为 API 19，现代 Android 路径保留。Robolectric 固定为 4.12.2：这是仍支持 API 19 的版本，4.13 起移除了该运行时。

  • 亮屏计时在 API 19 使用 PowerManager.isScreenOn()；关屏、待机和锁定时暂停，用量持久化和家长密码规则不变。面板状态这一路判据（Display.getState()）自 API 20 才存在，因此 API 19 仍只有电源管理一个判据，2.5.16 的双判据从 API 20 起生效，读不到时一律按「亮着」处理，不会因为接口缺失而冻结当天额度。
  • 界面提供旧版主题、图形资源和控件样式，不依赖原生 Material、VectorDrawable 或 API 21 的文字与按钮接口。
  • API 19 更新使用 AlarmManager 和独立服务；API 21 以上保留 JobScheduler。旧系统启用 TLS 1.2，仍验证主机、证书、APK 签名及版本。
  • API 19 通过系统安装器、在有效家长维护授权下确认安装；不继承进程重启前的授权，不清除原有密码或时长数据。
  • Android 4.4 没有 Lock Task，也没有本应用使用的 Device Owner 防强停策略。普通管理员仍启用时，PackageManagerService.deletePackageX 的 isPackageDeviceAdmin() 会拒绝直接卸载；系统可先停用管理员，因此仍须保持设置入口拦截。页面按实际状态区分两类保护。发现旧版设备所有者时拒绝不安全解除，不恢复出厂。

回归覆盖 API 19 的计时/关屏/重启、鉴权、界面资源、权限入口和更新路径，并保留 API 24、33 的相关测试。原生图形截图测试在 API 33 运行，不把预览当作真机截图。小米电视 2 的实机验证仍待 ADB 恢复，未验证厂商后台保活和遥控行为。

遥控器输入模式

2.5.7（versionCode 38）按数字键能力选择输入模式并提供本机手动切换；2.5.11（versionCode 42）把检测改成跨设备取并集，并让实测到的数字按键优先于能力报告；2.5.13（versionCode 44）删掉手动切换，输入模式只剩硬件判定这一条来源；2.5.14（versionCode 45）把判定不出来时的整屏数字盘换成一枚数字键盘图标，数字盘要按 OK 展开。两种输入方式均不依赖系统输入法（IME）、WebView 或触摸输入。家长验证、首次设置和修改密码、到时锁屏、每日时长、临时加时均须可在有实体数字键或仅有方向键、OK 的遥控器上完成。

  • 硬件检测：把每个非虚拟且带 SOURCE_KEYBOARD 或 SOURCE_DPAD 的 InputDevice 报告的数字键合成并集，普通数字键和小键盘数字键任一支持即算该数字存在；并集覆盖 0–9 就只用实体输入区，数字盘和图标都不出现。单台设备报不全不算作「没有数字键」，并集缺一字或检测结果未知时给一枚数字键盘图标，不按品牌或型号硬编码。hasKeys() 抛异常或返回长度不等于 20 的畸形结果按「该设备不提供数字」处理，一台设备的畸形答复不能否决其它设备的证据，整个查询抛异常时按未知处理、把数字盘留在图标后面，不能让验证页崩溃。设备按并集补齐后立即停止查询，不再询问后面的设备。
  • 实测优先：onPhysicalDigit(KeyEvent) 收到真正来自非虚拟设备的数字按键时写入 tvguard_remote 的 physical_digits_seen，并收起屏幕数字盘与图标——这是给厂商 keymap 报错留的后门。deviceId 未知（-1）、设备是虚拟设备或事件来自屏幕数字盘自身都不算证据，不能因为一次合成按键就把家长的数字盘收掉。
  • 读取顺序只剩两级：physical_digits_seen > 硬件检测。2.5.13 起 RemoteInputMode 的构造会删除旧版留下的 show_keypad、pad_pinned，因此升级后即使本机以前固定过数字盘，也重新由硬件决定；RemoteInputMode 不再暴露 toggle，LockActivity、AdminAuthActivity、PinDialog 不再有 handleKeyEvent 的切换分支，锁屏提示与 PinDialog 帮助文字相应改为只描述当前可用的输入方式。学习与判定变化只改变输入方式，不更改 PIN、计时或家长授权。
  • 数字盘的状态只有两个来源：digitsKnown（能力并集或实测证据，跨屏持久）与 padRequested（家长在本屏按过图标，不持久）。usesOnScreen() 为「未判定且已按过图标」，showsRequest() 为「未判定、没按过、且数字盘当前可用」。图标是 RemoteKeypad.padRequestButton(Context) 造的原生 Button（tag keypad_request，图形为自绘 KeypadGlyph 3×3 点阵），由 RemoteInputMode.requestButton() 交给三个入口界面挂进自己的文案列（entry_copy / copy），RemoteInputMode 不持有布局。handleKeyEvent(event) 在界面把按键交给数字盘之前先跑：图标有焦点时吃掉导航与 OK（DOWN 装填、UP 才 performClick，取消或长按重复都不触发），输入区有焦点时方向下或右把焦点交给图标；数字盘被禁用（冷却、服务恢复中）时 showsRequest() 为假，图标随之隐藏，syncRequestVisibility() 由 LockActivity.refreshUi() 与 AdminAuthActivity.render() 在 setEnabled 之后调用，并把已经落在图标上的焦点退回输入区。按图标只是展开数字盘，不授予任何家长权限；换一屏重新从图标开始。
  • Gate 与 PinDialog 导航：检测到数字键时默认聚焦输入区，直接按遥控器数字键；未判定时同样聚焦输入区，按方向下或右选中图标、OK 展开数字盘并聚焦第一个数字，从盘顶部按方向上回到输入区（setUpperFocusTarget），锁屏把该目标设为「家长管理」按钮。
  • 屏幕输入：展开数字盘后方向键选择数字，OK 输入；「删除」「确认」均有可聚焦的屏幕按钮。数字盘导航不能把方向左误当成删除。
  • 实体数字键输入：保留直接输入，输入后左键删除、OK 直接确认。返回取消当前输入，不能因此授予家长权限、解除锁定或更改额度。
  • 家长 PIN 保持 6 位遮罩、原有错误提示与失败冷却。修改密码仍需再次验证；数字盘按钮与实体数字键共用校验、授权和提交路径，不因输入方式放宽边界。每日时长和临时加时显示数字，沿用原有限额与今天生效规则。
  • Lock 默认聚焦「家长管理」，数字输入的硬件判定和数字盘图标不变。2.6.4 起，正确配置的家长密码在锁屏输入或独立验证页输入后立即解除当前锁定，再进入管理面板；不再依赖面板退出才放行。出厂密码只设置新密码，关闭首次设置后的面板不能自动解锁。
  • 保留暗色面板、显著的 DPAD 焦点和原有卡片对齐；验证门页与锁屏保留独立主题。隐藏时 Gate/Lock 居中、最大 560dp，PinDialog 恢复最大 560dp 单栏，未判定时这一栏在输入区下方多出一个居中图标；显示数字盘时分别沿用原最大 900dp 与宽屏最大 760dp 布局。隐藏数字盘不留空位，判定变化后重排输入区域，并将焦点保留在可见控件上，不改主面板列宽、间距或卡片布局。

发布前应检查完整数字键、跨设备拼出完整数字键、缺一字与检测未知时的输入模式，实测数字按键收起数字盘与图标、虚拟与合成按键不学习、旧版 show_keypad/pad_pinned 被清除且不再强制显示数字盘，以及隐藏后的布局与焦点；未判定的电视上还须检查图标是屏幕上唯一的数字输入提示、方向下或右可选中它、OK 才展开数字盘、冷却期间图标与数字盘一起隐藏、换屏后重新回到图标；同时检查两种输入路径、屏幕删除/确认、返回取消、PIN 遮罩、失败冷却、授权失效和锁屏两种入口。2.5.13 删掉切换按钮后没有人工兜底：厂商 keymap 报了 0–9 而遥控器实际没有数字键时，家长只剩实体输入这一条路，这类电视一旦遇到必须在检测上补证据而不是恢复按钮；2.5.14 的图标只补回「按一步拿到数字盘」，不改变这条判定。2.5.16 起还须在实机上确认待机这条路：额度用尽后放着不管，15 秒左右屏幕应当自己熄灭（以前被锁屏按着不放），按遥控器任意键后先看到锁屏；未锁定时按遥控器关机十分钟再开机，右上角「剩余」只该少掉真正看的那几分钟，不能少十分钟；锁屏在面板熄灭期间不得把电视点亮。2.5.17 起还要在实机上检查家长宽限这条路：锁屏输密码进面板、按返回键或用 <code>00</code> 退出，都应落到电视机桌面且不弹锁屏；此后随便打开哪个应用都不该再要密码，这是家长反馈的死循环本身。宽限的四个终点逐个验证：按遥控器关机等待机、重新亮屏先看到锁屏；面板里 <code>33 立即锁定</code> 立刻锁屏；跨到新一天锁屏回来；拔掉电源重开电视后锁屏回来。宽限期内右上角仍显示「剩余 00:00」，看进去的分钟仍计入今天已看，额度数字一个不减；孩子在锁屏按 HOME 拿不到宽限、仍被锁回。2.5.15 的一步式桌面豁免（离开桌面第一个窗口就失效）已随本版删除，不再按那套口径验收。2.5.18 起设置页不属于宽限，另按两分钟窗口验收：没输过密码时进设置立刻弹家长验证；输对一次密码之后两分钟内反复进出设置、应用详情、卸载确认页都不该再要密码；中途再输对一次密码要把这两分钟重新起算；输错密码不给免密；改密码那一步先要旧密码，成功后不该白送这两分钟；电视断电重开后不能继承上一次开机的窗口。2.5.19 起这两分钟是入场券、这次访问本身是通行证，还要按这条验收：输对密码后一直停在设置页面上不碰遥控器，两分钟过后仍然不该弹密码页；在菜单里换页面（设置→应用→应用详情→卸载确认）也不弹；按 HOME 或打开任意 APP 走出设置菜单后，再回设置必须立刻重新要密码；按遥控器关机进入待机、面板里 <code>33 立即锁定</code>、跨到新一天、断电重开这四种情况回到设置页都要重新要密码；屏保或面板熄灭期间不算还有人停在菜单里。宽限期内的锁屏口径不变：额度用尽、家长退出面板后锁屏不抢前台，但那两分钟和这次访问都管不着锁屏，放行期间额度用尽照样锁。同一版还要验证面板第五行 <code>77 清零今天已看</code>：方向键能走到这一行、按 OK 立即归零且没有二次确认框；「今天已看」回到 00:00、右上角立刻显示完整额度、每日额度与临时加时的数字一个都不该变；正在锁屏时清零后锁屏应自己退场，孩子回到应用不再被锁；关闭防护时这一行不出现，快捷码 <code>77</code> 与按钮是同一条路径。构建与自动化结果由最终发布验证汇总，不把原生渲染预览当作真机证据。小米电视 2 的 ADB 仍待恢复，不能宣称已通过该电视的实机数字盘验收。

计时与右上角

2.5.10（versionCode 41）处理 Sony BRAVIA 4K 2015 上确认的两件事：待机被算成观看时长，以及「今天不限时」时右上角完全空白。2.5.12（versionCode 43）把「今天不限时」这个状态本身删掉，角标因此只剩倒计时一种形态，待计时规则不变。2.5.16（versionCode 47）把「屏幕亮着」这一条判据换成两个部件同时作证，并删掉锁屏的强制保持亮屏。2.5.17（versionCode 48）的家长宽限不改这套口径：宽限只是把锁屏放下来，角标仍按剩余时间显示「剩余 00:00」，期间面板亮着的分钟照常计入今天已看，计时基线与封顶不变。2.5.18（versionCode 49）的两分钟窗口同样与计时无关；本版唯一影响计数器的动作是面板 77 清零今天已看，它把「今天已看」归零并重设计时基线（否则下一拍会把清零前的间隙补记回来），每日额度与临时加时的数字不变，之后的每一分钟照常按双判据计入。2.5.19（versionCode 50）的「停在设置菜单里就放行」也不碰计数器：它只让设置页不再弹密码页，熄屏与屏保期间既不刷新放行也不计费。

Sony 实机采样（只读 dumpsys，每 5–7 秒一次）给出的结论：

  • 遥控器 关机 确实会走到框架：Notifier.sendGoToSleepBroadcast → com.sony.dtv.intent.action.PRE_SCREEN_OFF → ACTION_SCREEN_OFF，mWakefulness 由 Awake 变 Asleep，Display Power: state=OFF、mGlobalDisplayState=OFF、screenState 2→0、interactiveState 1→0，且切换发生在一次采样之内（无中间态）。这一段本来就不计入当天额度。
  • 同一段 77 分钟待机里 uptimeMillis 前进了 69 分钟——Sony 在待机中持有 PARTIAL_WAKE_LOCK 'heat_control' 与 'WebApiWakeLock'，SoC 不 suspend，所以 2.5.10 的「靠开机时长识别待机」在这台机器上几乎不起作用，只有面板状态可靠。
  • 采样期间锁屏窗口是整机唯一的 SCREEN_BRIGHT_WAKE_LOCK 持有者、也是唯一的 mHoldScreenWindow；本机 mScreenOffTimeoutSetting=15000（15 秒），也就是说只要锁屏在屏幕上，框架的熄屏超时永远不会生效，电视不会自己进入待机。锁屏因此不再持有 FLAG_KEEP_SCREEN_ON，只保留 TURN_SCREEN_ON；LockActivity.launch() 在面板不亮时直接返回，唤醒后由 ACTION_SCREEN_ON 重新主张锁屏。
  • 同一段待机的前后，前台窗口、输入设备列表与 screen_brightness 都没有变化，不能当判据；面板状态（Display.getState()，与 dumpsys display 的 mState 同源）是目前实测唯一会随待机改变的第二个信号。

据此，2.5.16 的计时与锁屏口径是：

  • 计时基线是 SystemClock.uptimeMillis()，不是 elapsedRealtime()。后者在休眠期间照旧前进，而一次补跑的 tick 会把整段挂钟差当作观看时长扣进当天额度——Sony BRAVIA 4K 2015 上家长确认电视可以连续数十小时处于待机，并要求待机一律不计入。2.5.16 的实机采样给这条防线加了限定：本机的 uptimeMillis 在待机里照样前进（77 分钟待机走了 69 分钟，Sony 的 heat_control 与 WebApiWakeLock 让 SoC 不 suspend），所以时钟只能算「设备真 suspend 时的第二重保护」，把待机挡在外面的是面板状态。countedDelta() 同时封顶单个周期的补量（MAX_COUNTED_TICK_MILLIS，4 秒），主线程被卡住、看门狗补跑或服务重启都只会补一个周期。亮屏、灭屏、服务创建和解除锁定四个入口都重新对齐基线，因此熄屏的分钟不会在唤醒那一刻被追溯扣除。
  • 额度判定是「面板亮着且未锁定」，2.5.16 起由 PanelState.isLit() 回答：PowerManager.isInteractive()（API 19 用 isScreenOn()）与 Display.getState() == STATE_ON 两个判据同时成立才算，任一不成立即视为待机，doze 与屏保也算待机。锁屏、LockActivity.launch() 与计时共用这一个判据，避免出现两套「屏幕亮不亮」的口径。
  • 关屏、锁屏与待机都不计时；跨到更晚的日历日才由 Prefs.rollOverIfNeeded() 清零，时钟回拨不给免费的额度重置。
  • 右上角角标由 GuardService 持有：未锁定时 updateCountdown() 显示「剩余 MM:SS」，最后 5 分钟转红。2.5.10 曾在这天被家长密码解锁时把同一枚角标换成琥珀色「今天不限时」（showUnlimitedNotice()）并与面板的 today_override 提示对齐；2.5.12 把这一状态、这段提示和那一行标记一起删除——家长密码不再买时间，角标就只剩下倒计时一种形态，也不会再出现空白角标被孩子读成「防护已关」的情形。锁定态不显示角标，只有全屏黑幕与锁屏 Activity。
  • 悬浮窗权限缺失时不贴角标（API 23 起 Settings.canDrawOverlays），面板另有「倒计时未开启：需允许悬浮窗权限」警告；API 19/20 由清单权限决定，不存在运行时撤销。
  • CountdownOverlayTest 在 API 19/24/33 断言：模拟一小时深度休眠后 tick 不增加当天时长；tick 被饿 20 分钟后最多补 4 秒；熄屏十分钟不扣、唤醒后只从亮屏那刻开始计；未锁定时窗口里恰有一枚文本角标、文字以「剩余 」开头且额度接近 30 分钟减去已看时间，反复 tick 不叠加；面板给出 10 分钟临时加时后同一枚角标的剩余正好多出 600 秒；无悬浮窗权限时不贴任何窗口；额度耗尽时进入锁定且没有倒计时角标。2.5.16 另在 API 24/33 断言：电源管理仍报 Awake 而面板报 STATE_OFF 的十分钟一分钟都不算、回到 STATE_ON 后只补唤醒之后的两秒；面板报 STATE_DOZE 的十分钟同样不算（若第二判据失效，tick 会补满 4 秒封顶量，这两条断言必然失败）。OnScreenLockTest 断言锁屏窗口不再持有 FLAG_KEEP_SCREEN_ON、仍持有 FLAG_TURN_SCREEN_ON，且面板熄灭时 LockActivity.launch() 不启动锁屏、面板点亮后仍会启动。PrefsAuthTest 另断言旧版写下的 unlocked_today 在升级后的第一次构造 Prefs 时被删除，且删除后时长锁重新生效。

设置入口保护与恢复

2.5.9（versionCode 40）以普通应用恢复原有密码拦截为目标，不要求系统预装、root 或 Device Owner：每次进入设置页都要求家长密码，同时消除「输入密码后再次要求输入密码」的验证死循环。MainActivity.requireParent() 保护图标入口，GuardService / LockActivity 保持额度锁定，AppLockService 保护已识别的设置及卸载页面；三条路径分别验收，不能把图标有密码等同于系统设置受保护。

  • 无障碍声明 canRetrieveWindowContent=true，仅调用 getRootInActiveWindow() 获取所属包名并回收节点，不遍历控件、不读取或保存文字。查询可能返回空，窗口事件仍保留为识别来源；查询异常记录日志并在面板提示，定时回查继续重试。
  • 连接时清除旧前台和设置解析缓存，250 ms 回查重新查询当前窗口，不依赖重连后必定补发窗口事件。未知包变化时立即重新解析，查询失败约 1 秒重试，同一未知包正常约 30 秒重新识别；局部失败不丢弃已识别的受保护包。
  • isEnabled() 检查无障碍总开关及启用组件，兼容完整和缩写组件名；isConnected() 来自服务连接、解绑和销毁回调。配置已启用不代表服务正在运行。普通应用不能自动重新开启系统已关闭的无障碍权限。
  • 每次进入设置页都要求家长密码：AdminSession 有效不作为设置页通行证，验证页与时长锁屏照常拉起。Sony BRAVIA 4K 2015 上的死循环不是靠记住密码修的，而是靠下一条规则修的：管理面板是半透明窗口，它下面的设置页仍然可见并持续上报自己是前台窗口，拦截服务因此在面板之上反复拉起验证页；面板 onPause 会撤销会话，下一个验证页就真的再次要求输入密码，输入后循环重现。日志证据是 MainActivity 启动后约 0.15～0.4 秒紧跟一条 AdminAuthActivity 启动，循环到家长放弃为止。2.5.18 起这条规则只有一个放行来源：本次开机里最近一次正确密码之后的两分钟（见下面「家长密码的两分钟窗口」）；2.5.19 把这同一个放行延续成这次访问本身——输对之后只要前台还是已识别的设置页面就继续放行，走出菜单、待机、33 立即锁定、跨新一天或断电即止（见下面「停在设置菜单里的放行」）。
  • 拦截服务在自家家长界面在屏时一律不动手，这是现行唯一的防死循环机制：验证页可见、已授权面板可见或 GuardService 的家长界面租约有效都不再拉起验证页或锁屏，不依赖具体机型的前台窗口判定。家长会话本身不放开设置，每次进入仍要家长密码。
  • 2.5.17（versionCode 48）在这条规则之上加了一个例外，也只有这一个例外：家长从管理面板按返回键或 00 关闭面板 退出时，MainActivity.closePanel(true) 调 GuardService.grantParentGrace()，把宽限写进 tvguard_prefs（parent_grace_since 记授予时刻的 elapsedRealtime，parent_grace_from_lock 记是否从锁屏发出），随后交出屏幕且不补弹锁屏、黑幕一起撤。2.5.15 的 DesktopPass（一步式、由 AppLockService 解析 HOME intent 判定桌面、30 秒缓存）连同它的存储与测试全部删除——正是「离开桌面第一个窗口就失效」让换个 APP 又变成要密码。宽限期不再由 AppLockService.enforceForeground() 提前返回：2.5.17 当时是「宽限期内既不 LockActivity.launch() 也不 AdminAuthActivity.launch()，设置页一并放行」，2.5.18 把这两件事拆开——宽限只让 Prefs.isGuardActive() 回答「不锁」，设置页改由两分钟窗口放行，因此家长退出面板后额度用尽的锁屏不抢前台，而设置页在窗口之外照样要密码。GuardService.keepLockInFront() 与 showShield() 同样在宽限期内不动手。宽限不靠超时结束，只有四个入口：ACTION_SCREEN_OFF 广播（Prefs.endParentGrace()，重新亮屏先看到锁屏）、面板 33 立即锁定（lockNow() 先撤销宽限再锁）、跨新一天（rollOverIfNeeded() 一并清除）、断电重开（elapsedRealtime 小于授予时刻即判失效，宁可早锁不错放）。宽限只推迟「已经在屏的锁」：grantParentGrace() 记录的 fromLock 取自当时 locked || prefs.isLocked()，isGuardActive() 与 lockRequired() 只在 isParentGraceDeferringLock() 为真时不锁屏，额度还剩一些的白天输密码不会把当晚的第一次锁定推迟——那正是 2.5.12 删掉的「今天不限时」。宽限不写时长、不清额度、不改 dailyLimit/bonus：锁屏是被放下而不是被藏起来，期间面板亮着的分钟照常计入今天已看，角标仍显示「剩余 00:00」；孩子在锁屏按 HOME、验证页返回（closePanel(false)）都不产生宽限，照常锁定。 该授予时机属于历史规则，2.6.4 起由下文的验证成功路径取代。
  • 家长密码的两分钟窗口（2.5.18，versionCode 49）只服务设置页：Prefs.authenticate() 返回成功的那一刻把 elapsedRealtime 写进 tvguard_prefs 的 parent_pin_verified_at（noteParentPinVerified()），AppLockService.enforceForeground() 的设置页分支变成 isSettingsPackage(前台) && !prefs.isSettingsGateFree() 才 AdminAuthActivity.launch()（2.5.19 起 isSettingsGateFree() ＝两分钟窗口或下面的设置放行）。三处刻意不放行：setPassword() 不盖这个戳（写入一个密码不等于输入过当前密码，11 改密码 本来就要 verifyAgain() 先把旧密码输对）；onKeyEvent() 里连按 00 唤出验证页不看窗口（面板能改规则，必须每次验）；isGuardActive() 也看不到它（两分钟不能推迟额度用尽的锁屏）。窗口只活 PIN_WINDOW_MILLIS＝两分钟，任何一次成功输入都重新起算；读到一个未来时间即判失效，所以断电重开不能继承上一次开机的免密；跨新一天不影响它，因为它本来就只活两分钟。存储用 elapsedRealtime 与墙钟无关，管控进程被回收重启窗口仍在，与家长会话的 3 分钟超时互不相干。
  • 停在设置菜单里的放行（2.5.19，versionCode 50）是家长在实机上报的 bug：输过家长密码、正在设置菜单里操作，两分钟一到就被弹回密码页。实现是 Prefs 的第四项存储 parent_settings_seen_at，记「拦截服务上一次确实看到已识别的设置页面」的 elapsedRealtime；isSettingsHoldActive() 接受五分钟内的记录（SETTINGS_HOLD_MILLIS），noteSettingsPresence() 把写盘节流到三十秒一次，因为检查前台的 foregroundCheck 每 250 ms 跑一次而 SharedPreferences.commit() 是同步的。刷新在 AppLockService.refreshSettingsHold()：isSettingsPackage(前台) && PanelState.isLit(this) && prefs.isSettingsGateFree()，并且在「面板在屏／短时维护」这两条提前返回之前也调一次——管理面板半透明，它下面的设置页仍然上报前台，家长「输完密码就停在菜单里」看到的正是这一屏；熄屏与屏保不算有人在菜单里，沿用 2.5.16 的电源管理加屏面板双判据，缺判据时 fail open。花掉它的入口与宽限同源：前台被确认成别的包（enforceForeground() 的 else 分支 clearSettingsHold()）、ACTION_SCREEN_OFF、33 立即锁定（lockNow()）、跨新一天（rollOverIfNeeded() 一并清除），断电重开由「时间戳在未来」判失效，五分钟没人再看见设置页面也自己过期，因此拦截服务被回收不会把菜单一直敞着。自家 LockActivity／AdminAuthActivity 与 com.android.systemui 的前台窗口既不刷新也不算离开，否则会把 2.5.7 那条防死循环规则绕回来。它与两分钟窗口一样只管设置页：isGuardActive() 看不到它，额度用尽时设置页之上照样盖锁屏，00 唤面板照旧每次验。
  • 77 清零今天已看（2.5.18）是 GuardService.clearTodayUsage()：先要求 AdminSession.isActive()（否则 IllegalStateException），把内存里的 usedMillis 与 prefs.setUsedSeconds(0) 一起归零，并重设 lastTickUptime / lastTickElapsed——不重设就会把清零前那一段间隙补记到刚清白的计数器上；locked || prefs.isLocked() 时先 exitLock()（清锁定标记、撤黑幕、角标回来），否则只 updateCountdown(remainingMillis())。每日额度与 bonus 一个都不碰，所以它是「重置计数器」而不是「发时长」，也不动 parent_grace_* 与 parent_pin_verified_at。面板 ACTION_ROWS 第五行与 GRID 的 77 共用 MainActivity.executeAction() 这条授权路径，isActionAvailable("77") 与 33/44 一样只在防护开启时可用，隐藏时既不显示也不能被执行。
  • 只有显式维护授权短时放行系统页；管理员激活返回（含取消）、更新返回或维护到期后恢复拦截；未经验证按返回不露出原设置页。
  • AppLockServiceTest 覆盖当前窗口恢复、重连、解析重试、连接状态与维护边界，并断言「有效会话之上的设置页仍要密码」「维护结束后同一个设置页重新要求密码」；SettingsGateLoopTest 用真实的验证页→面板交接和「面板之下的设置页仍上报前台」复现死循环，断言面板在屏时不弹验证页也不弹锁屏、家长离开后这两分钟内的同一个设置页不再要密码、两分钟之后只要还停在设置菜单里也照样不弹（这一等就过了五分钟的有效记录上限，靠的是被持续看见而不是旧记录）、走出设置菜单再回来立刻重新要、时长用尽的锁屏在家长离开面板后回来（该用例销毁面板、不走 2.5.17 发放宽限的 closePanel(true) 退路）；ParentGraceTest 覆盖家长宽限：两条退路都发宽限、未经家长验证不宽限、宽限期内换 APP 都不再弹密码页、宽限只管锁屏而设置页按两分钟算、宽限不停表也不送时长、待机与 33 立即锁定、跨天、断电重开四种终点、进程被回收后宽限仍在、宽限不依赖拦截服务连接，以及额度还剩一天的白天输密码不会推迟当晚的锁屏；ParentPinWindowTest 覆盖两分钟窗口与 2.5.19 的设置放行：没输过密码时设置页要密码、真实验证页输对才发放、窗口内三种受保护页面（电视设置、小米设置、卸载确认）都放行、输错密码与 setPassword() 都不发放、任何一次成功输入都重新起算、走出设置菜单且两分钟到期后同一页面重新要密码、八分钟连续停在菜单里（含换页面）一次都不弹密码页、走出菜单立即结束放行、没付过密码时停在菜单里多久都不发放、无人续期的旧 sighting 五分钟后自己过期、熄屏不算有人在菜单里、待机与 33 立即锁定、跨新一天、断电重开四种终点、放行不推迟额度用尽的锁屏也不让 00 免密进面板、管控进程被回收后仍在、跨新一天只按自己的时钟结束；ClearTodayUsageTest 覆盖 77：清零把今天已看归零而每日额度与临时加时一个不动、清零后一分钟只计一分钟（重设计时基线）、待机依旧不计费、清零解除正在挂着的锁屏并让角标回来自建、没有家长会话被拒绝、快捷码 77 与第五行按钮按 OK 都立即清零且不再二次确认、结果落进存储能在管控进程重建后保留；MainActivityRemoteTest、MainActivitySettingsTest 验证图标鉴权和真实警告。自动化不替代电视上的桌面长按、应用详情和卸载入口验收，不能据此认定本次电视故障根因。

防卸载附加保护

普通设备管理员仍启用时，系统的直接卸载检查会拒绝移除；这不等于所有设置流程都无法卸载，也不等于要求本应用密码。设置入口拦截才是日常保护主线。

  • 家长在面板按 55，经系统 ACTION_ADD_DEVICE_ADMIN 确认页激活；应用不静默激活。仅在限时维护授权下打开该页，返回后结束维护并按 isAdminActive 读回真实结果。
  • 系统 DeviceAdminAdd 的部分流程可通过 uninstallPackageWithActiveAdmins() 停用并卸载。onDisabled 发生在停用后，只能撤销旧授权并尝试拉起密码门，不能否决已经完成的操作。
  • 关闭防护仍走 DeviceProtection.remove() 的家长确认和读回核验，不恢复出厂。普通模式不承诺阻止系统强停、清除数据或未识别的厂商入口。
  • UninstallProtectionTest 与 DeviceProtectionTest 覆盖 API 19/24/33 的激活维护、返回恢复、停用后重新验证、策略读回与系统确认页无法解析的情况；不是实际卸载验收。

私钥保存在仓库外；默认读取 ~/.config/tv-kids-guard/signing.properties，也可用 TVGUARD_SIGNING_PROPERTIES 指定：

2.6.0 计费日与 HTTP 后台

GuardService 保存内存计费日，每次 tick 和 persist 都与 Prefs.getUsageDay() 对齐；Prefs 的其他 getter 已换日时，服务仍能重置内存与旧锁屏，保留新一天主动设置的锁。家长宽限读取本身先执行换日。DailyRolloverTest 覆盖 API 19、24、33 的读写次序与完整次日 30 分钟锁定。

ParentWebService 是独立前台服务，开机、覆盖升级及进入应用时启动，计时防护停用后仍可远程恢复。ParentHttpServer 在电视监听 0.0.0.0:8888，以有界线程池、请求大小与超时限制处理 HTTP；静态文件内置于 APK，业务请求统一交给主线程，复用 GuardService 的时长和锁定操作。ParentWebController 的请求能力单独验证，不使用 AdminSession.grant。

ParentWebCredentials 独立保存网页账号（默认 admin/admin）、随机 salt 与 PBKDF2WithHmacSHA1 哈希，修改需当前网页密码。新账号 1–64 个字母、数字、下划线或连字符，新密码不限制位数，只要求非空且两次输入一致；修改后已有网页会话失效。电视 PIN 的远程复验只共享本地失败冷却，不授予设置窗口。ParentWebSession 使用随机 HttpOnly/SameSite cookie 与 CSRF token，30 分钟无请求过期；实际网络传输为用户要求的 HTTP。

HTTP 只接受明确 IP 或 localhost 的 Host；写操作要求 JSON，校验 Origin 与 CSRF，不提供 CORS。后台菜单 13 只检查下载，系统安装与 55 的管理员启用仍由电视原生确认；系统 Lock Task 生效时，44 返回明确错误，须在电视先退出原锁定任务。

2.6.1 的立即锁定作为新的验证边界：GuardService 同时清除 AdminSession、家长宽限、设置 hold/PIN 窗口与 parent UI lease，再重新建立锁屏；MainActivity.closePanel 仅允许仍持有效家长授权的退出发放宽限。浏览器使操作前在途的 state 响应失效，强制读取操作后的状态，避免旧轮询覆盖锁定反馈。

2.6.2 的 WindowVisibility 在真实 decor attach 后绑定当前 ViewTreeObserver，避免 Android 4.4/7 的 floating observer 在 merge 时丢失 OnDrawListener。首帧 draw traversal 结束后的回调再次核对焦点与显示状态，之后每秒续报；GuardService 的锁屏可见租约为 3 秒，独立于持久锁标记。密码页的启动等待只暂停重拉，不提前撤罩，300ms onUserLeaveHint 回退同样遵守启动等待；启动等待到期恢复拉锁。LockCoverageTest 在 API 19、24、33 验证首帧前不露画面、可见续报、失焦/超时恢复及慢启动。锁定/解除与解除原因、覆盖丢失/续报超时写入 TvGuard 日志，不记录密码。

2.6.3 网页布局与验收

2.6.4 原生认证与单运行时

TvGuardApplication 在应用启动时检查同 UID、同默认进程名的重复进程，以 /proc/<pid>/stat 字段 22 的内核开始时间选择新运行时，避免 PID 回绕误判；同 tick 用 PID 确定唯一胜者。它排除其他 UID 和冒号子进程，并记录重复进程清理事件。生产故障是家长认证与管控服务分处两个默认进程，静态 AdminSession 无法共享。

GuardService.releaseAfterParentPin() 只由两条正确 configured PIN 分支调用，要求当前家长会话与本机 PIN 验证窗口；它先同步当前计费日及旧锁，再授予已有家长放行并解除锁定。远程复验、出厂设置和旧会话不会调用此入口。MainActivity.closePanel() 仅保留已有放行；熄屏和跨日撤销旧会话，认证入口先换日再写新验证记录。新增 ConfiguredPinUnlockTest 与 TvGuardApplicationTest 覆盖即时放行、无数值变化、首次设置、边界重验、跨午夜、默认进程筛选及 PID 回绕。

网页仅保留名称、字段、状态、按钮和错误，物理删除按钮说明、表单解释及对应脚本和样式。原有确认操作、CSRF、独立网页登录账号与状态刷新竞态处理继续保留。

2.6.5 旧电视启动接管与固定导航

Sony API 24 真机发现旧 Guard/web 进程在覆盖安装和 am force-stop 后仍残留，应用读取其他同 UID 进程的 /proc/<pid>/stat 返回 FileNotFoundException，而 adb shell 可读。2.6.4 的进程出生时间判断因此没有清理旧服务。

TvGuardApplication 现在用应用私有 runtime-start.lock 的 FileChannel 独占锁串行化启动接管，持锁后重新查询 ActivityManager，只结束同 UID、精确默认进程名、有效 PID 且非自身的实例。锁只覆盖启动清理，随后立即释放；不依赖 PID 大小、回绕或其他进程的 /proc。锁失败以明确异常结束启动，不静默制造第二套管控状态。当前 manifest 的所有组件都运行于默认进程；不要新增 android:process 而不重新审核该契约。

网页为固定导航与各设置页常驻表单，44/55 确认在系统页完成；沿用原接口、独立网页登录会话、CSRF 和操作后重新读取状态的规则。

2.6.8 深入排查与回归

Prefs 持久授权保存开机绑定：优先 Settings.Global 的 boot_count，旧系统尝试 /proc/sys/kernel/random/boot_id。构造时先清不同 boot 的 grace、PIN 窗口和 settings hold，再允许状态读取。两种标识均不可用时，只接受当前 runtime 真正建立的授权，旧 runtime 状态在任何读取前失效；此分支不再保证内存回收后免密恢复。当前 runtime 的新授权不因迟到 BOOT_COMPLETED 失效，MY_PACKAGE_REPLACED 不作为新开机。密码、额度、已看、加时、显式锁与防护开关不在该清理范围内。

GuardService 的 33 在撤销会话后同步调用 AdminAuthActivity.invalidateForLock，避免旧密码页在 onPause 前以半截输入解开新锁。AdminAuthActivity 的首次设置资格在 resume、心跳、提交均重验；ParentWebController 的 11 在首个配置 PIN 保存成功时还会同步撤销旧 factory 授权，覆盖认证页尚未创建的交接窗口。

原生加时按提交时剩余额度校验并捕获业务拒绝。网页 44 使用绑定 Authorization 与 2.5 秒窗口的管理员解除标记；结束、失败、超时、退出及 close 均清理，迟到轮询不能复活旧操作。GuardDeviceAdmin 只跳过仍有效的本次网页解除，不跳过外部停用。

网页 request/loadState/perform 按 authGeneration 丢弃旧会话响应与错误，读取任务仅清除自己的 pending 引用；退出 00 的可用性及点击均不依赖 state。MainActivity/PinDialog 保留系统 TV_POWER。

新增失败复现覆盖 BootAuthorizationTest、ConcurrentBonusTest、FactorySetupConcurrencyTest、OldAuthAfterWebLockTest、RemoteAuthTest 及 ParentWebControllerTest。各类局部结果和失败证据位于本机 security-audits；最终集成结果以本轮完整报告为准。
